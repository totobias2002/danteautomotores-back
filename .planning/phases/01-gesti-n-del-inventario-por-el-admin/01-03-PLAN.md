<objective>
Consolidar el negocio en una sola agencia fija: los autos se asocian solos a "la agencia" (D-06), el panel solo edita sus datos (D-07) y el backend deja de exponer el alta y la baja de agencias. Cubre la parte de crear y editar de ADM-02 contra la API real, con los mensajes del backend visibles en los forms.

Objetivo de la fase (ROADMAP, textual; no está en formato de user story): "La única cuenta admin gestiona el inventario completo de autos (datos, fotos, estado y destacados) desde el panel, contra la API real y con errores manejados de forma uniforme".

Purpose: hoy el form obliga a elegir una agencia y el panel deja crear y borrar varias. El negocio es una sola agencia y el panel no debe sugerir otra cosa (CONTEXT "Specific Ideas"). La agencia la siembra 01-02 (D-05); si en la base de dev hay varias, "la agencia" es la de menor id y las demás no se tocan.
Output: `AgenciaRepository.findFirstByOrderByIdAsc`, `PublicacionService.obtenerAgenciaUnica`, AgenciaController/Service sin crear ni eliminar, tests `PublicacionServiceTest` y `AgenciaControllerTest`, y front sin selector de agencia ni CRUD de agencias.

Reversibilidad (D-05 en CONTEXT): reversible. La tabla, la entidad y la FK `publicaciones.agencia_id` se conservan, así que volver a varias agencias es reagregar endpoints y el selector.
</objective>
